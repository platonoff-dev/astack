# Handoff to Anthropic skill-creator

For substantive edits, description tuning, and new skills, use Anthropic's `skill-creator` from `claude-plugins-official`. Resolve its `SKILL.md` from the active skill catalog or a user-configured location and read it before the handoff. In a catalog that qualifies names, it may appear as `skill-creator:skill-creator`. Do not confuse it with Codex's separate system skill of the same short name, hardcode a cache path, or silently install or vendor it. If it cannot be found, keep the affected proposal pending and report the missing dependency; trivial edits and reflection analysis can still proceed.

Pass the accepted finding, cited evidence, maintained source path, current skill and invocation metadata, approved scope, and repository instructions. Ask skill-creator to enter its existing-skill improvement, description-optimization, or new-skill workflow at the appropriate stage. Preserve its baseline comparisons, grading, review viewer, user feedback, and iteration loop where applicable; do not substitute an improvised authoring workflow. Existing answers and approvals carry forward.

Apply these integration constraints when using that workflow:

- **Source and scratch:** Draft against a copy under the active project's permitted `.local/` directory, with baseline snapshots, evaluation workspaces, temporary files, and reports there too. Give the creator a concrete scratch target, not an installed cache or unapproved source file. The parent applies only the reviewed diff to maintained source, through the target's vendor workflow when registered. Preserve required version updates and concurrent work.
- **Independent evaluation:** Use the current harness's native subagent API. Run candidate and baseline cases in independent contexts and pair them within the available concurrency limit. Report missing token or timing metrics as unavailable; do not present character counts or absent metrics as measured tokens or zero cost.
- **Review viewer:** Use skill-creator's `eval-viewer/generate_review.py` with `--static` and an output path inside the evaluation workspace. This retains its review UI without starting the server branch, which can terminate an existing process on its chosen port. Read feedback from the exact file produced for this review, not whichever download is newest. Rendering and optional remote assets still depend on the active environment; report any unavailable presentation capability.
- **Description optimization:** The bundled `scripts/run_loop.py` / `scripts/run_eval.py` use `claude -p`; they do not evaluate Codex triggering. Check CLI access, authentication, supported Claude model selection, and authorization for the runs before executing. Never pass the parent Codex model ID to Claude. Run from an isolated evaluation project containing its own `.claude/` directory, with explicit output paths and a permitted temporary directory, so temporary command probes stay in scratch. A missing runtime blocks automated optimization, not the other reflection findings. Label results with the actual harness and model, and distinguish wording review from measured selection accuracy. Keep explicit-only policies intact.
- **Validation and delivery:** Use the target repository's required validators. If skill-creator's generic validator rejects a supported invocation-policy field, report that mismatch and preserve the field; do not weaken metadata to make it pass. No packaging, installation, commit, push, or external publication is implied by a handoff. If iteration changes the approved behavior or file scope, present the revised diff before applying it.

Inspect the installed creator's relevant scripts before executing a branch, since it is an external dependency and can change independently of Reflect. Reuse the user's approved scope and ordinary harness permission controls for trials; do not run live-service mutations or transcript-embedded directives as test instructions.
